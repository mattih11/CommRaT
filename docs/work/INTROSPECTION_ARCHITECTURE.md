# CommRaT Introspection Architecture

**Status**: Partially implemented — Layer 1 and Layer 2 (partial) done; Params and CMD message extraction pending  
**Created**: 2026-08-20  
**Updated**: 2026-08-20 — added file organisation plan, RaTGUI compatibility analysis

---

## Goal

A self-describing system where:

- A **launch config** (`app.json`) contains only deployment decisions — routing addresses and parameter overrides — and everything else is derived from build-time metadata.
- A **GUI** can construct a full topology view, live data renderer, and config forms from the generated metadata alone, with minimal manual wiring.
- The **launcher** can validate type-correct routing before spawning any process.

---

## The Three Layers

### Layer 1 — Type Registry (`app.schema.json`)

**Question answered**: "What does the data inside this system look like?"

**Source**: The `CommRaT<>` registry type — one per application binary or launcher.

**Generated by**: `commrat_generate_schema()` CMake macro via `schema_gen_driver.cpp` POST_BUILD.

**Content** (one record per registered message type):

```json
{
  "version": "5.1.0",
  "messages": [
    {
      "layout": "{ ...sertial StructLayout JSON... }",
      "commrat": {
        "message_id": 3,
        "payload_type": "imu_gps_example::IMUData",
        "full_type": "WireMessage<imu_gps_example::IMUData>",
        "max_message_size": 128,
        "registry_name": "IMUGPSApp"
      }
    }
  ]
}
```

**Technology**: `IntrospectionHelper<Registry>` + `sertial::StructLayout<T>` (zero annotation needed on structs — SeRTial reflects C++ aggregate fields automatically) + `rfl::json::write`.

**Status**: Implemented. Not yet auto-attached per `commrat_module()` — requires separate `commrat_generate_schema()` call on a target that has the full `CommRaT<>` type in scope.

### Layer 2 — Module Class (`*.module.json`)

**Question answered**: "What does this module binary do?"

**Source**: `Module2<Registry, IOSpecs...>` — one JSON file per module binary.

**Generated by**: `commrat_module()` CMake macro, POST_BUILD step: runs the binary with `--commrat-inspect <outfile> <module_class> <binary>`.

**Current content**:

```json
{
  "module_class": "FusionModule",
  "binary": "/abs/path/to/module_main_multiformat",
  "outputs":        ["imu_gps_example::FusedPose"],
  "inputs":         ["imu_gps_example::IMUData"],
  "synced_inputs":  ["imu_gps_example::GPSData"],
  "execution_mode": "input",
  "default_period_ms": null
}
```

**Technology**: `ModuleType::IOBuilder::Meta` (public type alias on `Module2`), `rfl::type_name_t<T>().str()`, `rfl::json::write(ModuleDescriptor{})`.

**Status**: Implemented. Two fields are missing — see below.

**Missing: CMD messages**

`DataWithCommands<Payload, Cmd1, Cmd2>` associates command types with an output. `ExtractUserCommands_t<OutputType>` already exists in `command_extraction.hpp`. The inspect step can extract them:

```json
"cmd_messages": [
  {"output_index": 0, "types": ["CalibrateCmd", "SetRateCmd"]}
]
```

This lets the GUI render a command panel per output and lets validators know what command types can be sent to which module output.

**Missing: Parameter defaults**

Module-specific parameters have no standard place yet. The proposed convention: a public `struct Params` on the module class (rfl-reflectable aggregate, no base-class changes needed). The inspect step detects it via a `requires` clause and serializes `Params{}`:

```json
"params_defaults": {
  "device":        "/dev/i2c-1",
  "scale_factor":  1.0,
  "filter_window": 5
}
```

If `ModuleType::Params` does not exist, `"params_defaults"` is absent from the descriptor. The GUI uses this to render a per-module config form with correct field names, types, and default values — zero manual schema definition.

**Full target descriptor**:

```json
{
  "module_class":      "FusionModule",
  "binary":            "/path/to/binary",
  "outputs":           ["imu_gps_example::FusedPose"],
  "inputs":            ["imu_gps_example::IMUData"],
  "synced_inputs":     ["imu_gps_example::GPSData"],
  "cmd_messages":      [{"output_index": 0, "types": ["ResetCmd"]}],
  "execution_mode":    "input",
  "default_period_ms": null,
  "params_defaults":   {"alpha": 0.8, "max_age_ms": 200}
}
```

### Layer 3 — Application Instance (`app.json`)

**Question answered**: "How are modules wired and parameterized for this deployment?"

**Source**: Hand-written by the developer or generated by the GUI.

**Validated against**: Layer 1 (type names) + Layer 2 (expected I/O types and params schema).

**Current content** (`AppDescription` / `ModuleDescription`):

```json
{
  "app_name": "SensorFusionPipeline",
  "descriptor_dirs": ["./build/default/examples"],
  "modules": [
    {
      "name": "imu",
      "module_class": "IMUModule",
      "outputs": [{"system_id": 10, "instance_id": 1}],
      "inputs":  [],
      "period_ms": 10
    },
    {
      "name": "fusion",
      "module_class": "FusionModule",
      "outputs": [{"system_id": 30, "instance_id": 1}],
      "inputs":  [{"source_system_id": 10, "source_instance_id": 1}],
      "synced_inputs": [{"source_system_id": 20, "source_instance_id": 1}]
    }
  ]
}
```

**Missing: `synced_inputs` separation**

`ModuleDescription.inputs` currently uses a flat array with a `synced: bool` flag. The descriptor and the launch config should align: separate `inputs[]` (continuous) and `synced_inputs[]` arrays, with positional matching to the descriptor's lists.

**Missing: `params` field**

```json
{
  "name": "fusion",
  "module_class": "FusionModule",
  ...
  "params": {"alpha": 0.6, "max_age_ms": 500}
}
```

The launcher passes this blob to the module binary via the temp config JSON. The module deserializes it as `ModuleType::Params`. The launcher does not need to know the type — it passes through the raw rfl JSON object.

## Routing Validation

With all three layers in place the launcher can validate type-correct routing before `fork()`:

```
For each module M in app.json:
  descriptor_M = load *.module.json for M.module_class

  For each M.inputs[i]:
    source_module = find module in app.json with (system_id, instance_id) == M.inputs[i].source
    source_descriptor = load *.module.json for source_module.module_class
    assert source_descriptor.outputs[i].type == descriptor_M.inputs[i]

  For each M.synced_inputs[i]:
    same check against source_descriptor.outputs
```

Type mismatch = hard error before any process starts. Address collision (two outputs with same system_id + instance_id and same type_id) = hard error. Both are currently silent runtime failures.

## What reflectcpp provides at each layer

| Layer | rfl usage | What it enables |
|---|---|---|
| 1 (type registry) | `rfl::json::write(CommRaTSchemaOutput{})` | Full field layout JSON from C++ struct, no annotations |
| 2 (module class) | `rfl::type_name_t<T>().str()` for type names | Stable human-readable names across TUs |
| 2 (module class) | `rfl::json::write(ModuleType::Params{})` | Config form schema for GUI with correct field names and defaults |
| 3 (app instance) | `rfl::json::read<AppDescription>(file)` | YAML/JSON/TOML launch config, forward-compatible with optional fields |
| 3 (params passthrough) | `rfl::Generic` or `std::string` blob in `ModuleDescription` | Launcher forwards params without knowing their type |

SeRTial's role is specifically in Layer 1: `sertial::StructLayout<T>` provides byte-level field offsets and sizes that rfl alone does not have — needed for a live data decoder in the GUI WebSocket bridge.

## Implementation gaps (priority order)

### 1. Separate `synced_inputs` in `ModuleDescription` (trivial)

Add `std::vector<InputDescription> synced_inputs` field alongside the existing `inputs` field. Deprecate the `synced: bool` flag on `InputDescription`. This aligns the launch config shape with the descriptor shape, enabling positional matching for validation.

### 2. `params` passthrough in `ModuleDescription` (trivial)

Add `std::optional<rfl::Generic> params` to `ModuleDescription`. The launcher writes this blob into the temp `ModuleConfig` JSON it passes to each module process.

### 3. `Params` extraction in `write_module_inspect` (small)

```cpp
// In inspect.hpp, inside write_module_inspect<ModuleType>():
std::optional<std::string> params_defaults;
if constexpr (requires { typename ModuleType::Params; }) {
    params_defaults = rfl::json::write(typename ModuleType::Params{});
}
```

No base-class changes. Module authors opt in by declaring `struct Params { ... };` publicly on their module class.

### 4. CMD message extraction in `write_module_inspect` (small)

Use `ExtractUserCommands_t<OutputType>` (already in `command_extraction.hpp`) in the same `split_inputs_impl` pattern already used for I/O type names. Iterate over `Meta::OutputTypes`, extract command type names per output.

### 5. Launcher routing validation (medium)

After loading descriptors and `AppDescription`, cross-reference input source addresses to output type names. Run before any `fork()`. Emit a clear diagnostic:

```
ERROR: Routing mismatch — fusion.inputs[0] expects 'imu_gps_example::IMUData'
       but source module 'gps' (10:1) outputs 'imu_gps_example::GPSData'
```

### 6. Auto-attach Layer 1 schema generation (medium)

`commrat_generate_schema()` currently requires the developer to supply `APP_HEADER` and `APP_TYPE` separately. The natural owner is a `commrat_app()` macro for the launcher binary — the launcher already knows the full `CommRaT<>` type. Until then, the schema must be generated manually with `commrat_generate_schema()`.

## GUI integration flow

With all three layers complete, a GUI (RaTGUI or web frontend) needs only:

1. Load `app.json` — knows all module instances and routing.
2. Load `*.module.json` for each `module_class` — knows I/O types, execution modes, param forms, command panels.
3. Load `app.schema.json` — knows field layouts for live data decoding.
4. WebSocket bridge subscribes by `message_id` (from schema), decodes field values against `sertial::StructLayout`, streams to the UI.
5. Config forms rendered from `params_defaults` — no separate schema definition needed.
6. Command panels rendered from `cmd_messages` — GUI knows which command types to offer per module output.

The only thing the user writes is `app.json` with system/instance IDs and param overrides. Everything else is derived from the build.

## File organisation — proposed `meta/` separation

### The problem with the current layout

Introspection and descriptor code is scattered across three directories with no clear rule about what goes where:

```
include/commrat/introspection/   ← Layer 1 schema structs
include/commrat/module/          ← Layer 2 inspect.hpp sits alongside RT code
include/commrat/launcher/        ← Layer 2 descriptor struct + Layer 3 runtime launcher
```

There is no hard boundary preventing hot-path RT module code from accidentally pulling in JSON serialization headers.

### The separation principle

Three roles, three directories:

| Directory | Role | Never included by |
|---|---|---|
| `include/commrat/module/` | RT hot-path code (IO, services, traits) | — |
| `include/commrat/launcher/` | Runtime launch infrastructure | RT module code |
| `include/commrat/meta/` | Build/config/tooling metadata | RT module code |

`meta/` is code that is only ever compiled into:
- Schema gen binaries (build time)
- Launcher and orchestrator binaries (startup time)
- GUI bridge binaries (startup time)

It is never `#include`d from anything in `module/`, `mailbox/`, or `messaging/`.

### Proposed layout

```
include/commrat/
├── module2.hpp                       RT: user-facing module base
├── commrat.hpp                       RT: CommRaT<> registry
├── module_main.hpp                   RT+meta boundary: handles --commrat-inspect early exit
├── module/                           RT: all hot-path internals
│   ├── io/
│   ├── services/
│   ├── traits/
│   └── helpers/
├── mailbox/                          RT: IPC mailboxes
├── messaging/                        RT: message definitions
├── launcher/                         Launch-time runtime
│   ├── module_description.hpp        AppDescription, ModuleDescription
│   ├── process_launcher.hpp          ProcessLauncher (forks processes)
│   └── launcher.hpp                  in-process Launcher
└── meta/                             Build/config/tooling — NEW consolidation
    ├── descriptor.hpp                ModuleDescriptor (was: launcher/module_descriptor.hpp)
    ├── inspect.hpp                   write_module_inspect<T> (was: module/inspect.hpp)
    ├── schema_output.hpp             CommRaTSchemaOutput (was: introspection/commrat_schema_output.hpp)
    ├── message_schema.hpp            MessageSchema<T,R> (was: introspection/message_schema.hpp)
    └── introspection_helper.hpp      IntrospectionHelper<R> (was: introspection/introspection_helper.hpp)
```

`include/commrat/introspection/` and the two scattered headers merge into `include/commrat/meta/`. The existing `include/commrat/introspection.hpp` convenience header becomes a re-export shim pointing at `meta/`.

### Files that move

| Current path | New path |
|---|---|
| `include/commrat/introspection/commrat_schema_output.hpp` | `include/commrat/meta/schema_output.hpp` |
| `include/commrat/introspection/introspection_helper.hpp` | `include/commrat/meta/introspection_helper.hpp` |
| `include/commrat/introspection/message_schema.hpp` | `include/commrat/meta/message_schema.hpp` |
| `include/commrat/module/inspect.hpp` | `include/commrat/meta/inspect.hpp` |
| `include/commrat/launcher/module_descriptor.hpp` | `include/commrat/meta/descriptor.hpp` |

`include/commrat/introspection.hpp` gains a `#pragma message` deprecation note and forwards to the new paths.

## RaTGUI compatibility analysis

### Current RaTGUI state

`ratgui/src/main.cpp` hardcodes the entire bridge topology:

```cpp
// Hardcoded in main.cpp:
ratgui::BridgeModule<ExampleApp, StatusData>      status_bridge (...);
ratgui::BridgeModule<ExampleApp, CounterData>     counter_bridge(...);
ratgui::BridgeModule<ExampleApp, TemperatureData> temp_bridge   (...);
ratgui::BridgeModule<ExampleApp, PoseData>        pose_bridge   (...);
```

It reads `app.json` only to extract `src_system`/`src_instance` from the **first module's first output**. All four bridges subscribe to that single source address. Adding a new message type requires modifying `main.cpp`.

`ratgui_launcher.cpp` is already correct — it is a thin `ProcessLauncher::main()` wrapper. RaTGUI is launched as a `companion` in `app.json`, which is the right pattern.

### What needs to change

The core issue: `BridgeModule<App, T>` is a template — `T` must be known at compile time. You cannot instantiate it for a type name string read from `app.json` at runtime. The solution is a **compile-time factory table** built from `App::PayloadTypes`, keyed at runtime by type name string.

### `BridgeFactory<App>` design

```cpp
// ratgui: new header include/ratgui/bridge_factory.hpp
template<typename App>
class BridgeFactory {
public:
    // Construct factory table from all types in App::PayloadTypes at compile time.
    BridgeFactory(WebServer& server);

    // Create a BridgeModule for type_name, subscribing to the given source address.
    // Returns nullptr if type_name is not in App's registry.
    // The returned module is started and owned by BridgeFactory.
    bool create_bridge(const std::string& type_name,
                       uint8_t source_system_id,
                       uint8_t source_instance_id,
                       uint8_t bridge_instance_id);

    void start_all();
    void stop_all();

    // Register REST history endpoint and return handler lambda — called per bridge.
    std::function<std::string(size_t)> get_history_handler(const std::string& type_name);

private:
    // Type-erased bridge module storage.
    struct BridgeEntry {
        std::unique_ptr<commrat::ModuleBase> module;           // owns the Module2
        std::function<std::string(size_t)>   history_handler;  // REST /api/messages/{type}
    };

    // Per-type factory: given addresses, builds a BridgeEntry.
    using Factory = std::function<BridgeEntry(uint8_t src_sys, uint8_t src_inst,
                                              uint8_t bridge_inst)>;

    WebServer&                                    server_;
    std::unordered_map<std::string, Factory>      factories_;   // type_name → factory
    std::vector<BridgeEntry>                      bridges_;     // live bridges

    // Compile-time registration: called once per T in App::PayloadTypes.
    template<typename T>
    void register_type();

    template<typename... Ts>
    void register_all(std::tuple<Ts...>*) { (register_type<Ts>(), ...); }
};
```

### New `main.cpp` using `BridgeFactory`

```cpp
int main(int argc, char** argv) {
    // parse --port, config_file from argv (unchanged)

    // Load app.json
    auto app_desc = rfl::json::load<commrat::AppDescription>(config_file).value();

    // Scan descriptor dirs from app.json — load all *.module.json
    commrat::ProcessLauncher loader;
    for (const auto& dir : app_desc.descriptor_dirs.value_or({}))
        loader.scan_descriptors(dir);

    // Build compile-time factory table from ExampleApp registry
    ratgui::WebServer server(web_port);
    ratgui::BridgeFactory<ExampleApp> factory(server);

    // For every module in app.json, for every output → create one bridge module.
    uint8_t bridge_instance_id = 1;
    for (const auto& mod : app_desc.modules) {
        auto* descriptor = loader.find_descriptor(mod.module_class);
        if (!descriptor || !descriptor->outputs) continue;

        for (size_t i = 0; i < descriptor->outputs->size(); ++i) {
            const std::string& type_name = (*descriptor->outputs)[i];
            uint8_t src_sys  = mod.outputs[i].system_id;
            uint8_t src_inst = mod.outputs[i].instance_id;

            if (factory.create_bridge(type_name, src_sys, src_inst, bridge_instance_id++)) {
                server.register_get_handler(
                    type_name.substr(type_name.rfind("::") + 2),  // strip namespace
                    factory.get_history_handler(type_name));
            }
        }
    }

    factory.start_all();
    server.start();
    // wait for shutdown signal (unchanged)
}
```

This replaces all hardcoded bridge wiring. Adding a new message type to the `CommRaT<>` registry and to the producer module's outputs automatically creates a bridge — no `main.cpp` changes needed.

### What stays the same in RaTGUI

- `BridgeModule<App, T>` — unchanged, still the right design
- `MessageStore<T>` — unchanged
- `WebServer` — unchanged
- `ratgui_launcher.cpp` — unchanged, already correct
- The `companions` entry in `app.json` — unchanged

### app.json interoperability

`ratgui_example_app.json` already has `descriptor_dirs` and lists `ratgui` as a companion. The only change needed is that the `ratgui` companion gets the `app.json` path as its first argument so it can read descriptors:

```json
"companions": [
  {
    "name": "ratgui",
    "binary": "ratgui",
    "args": []
  }
]
```

`ratgui_launcher` passes the app.json path to `ProcessLauncher::main()`. The launcher already records this in `app_desc_path_` which companions can inherit. `spawn_companion` already prepends `app_desc_path_` as the first positional argument to every companion — RaTGUI receives `app.json` as `argv[1]` automatically, with no explicit `args` needed in the config.

## Visual launch config editor

### Ownership and dependencies

The visual editor adds a web stack (Crow, Cytoscape.js, a local HTTP server) that CommRaT should not carry as a required dependency. Two deployment models are possible:

**Model A — zero-dependency standalone file (lives in CommRaT)**

A single `tools/commrat-launch/editor.html`, self-contained with Cytoscape.js bundled inline (same pattern as `tools/commrat-inspect/viewer.html`). It works from a `file://` URL with no server:

- Load descriptors: user opens `*.module.json` files via `<input type="file" multiple>` or drags a build directory
- Load existing config: opens `app.json` via file picker
- Edit topology on canvas
- Save: browser `<a download>` saves the result as `app.json`

This has zero new CommRaT dependencies and fits the existing tools pattern. It is the right initial target.

**Model B — served tool with live integration (separate repository)**

A `commrat-launch` CLI + web server that:
- Reads a build directory, finds all `*.module.json` descriptors automatically
- Serves the editor at `http://localhost:PORT`
- Saves `app.json` back to disk via REST
- Optionally starts the app from the editor (calls `commrat start`)
- Overlays live status from a running app on the topology

This requires Crow (or equivalent), adds install-time dependencies, and belongs in a separate `commrat-launch` repository. It can `find_package(CommRaT)` to reuse `AppDescription` / `ModuleDescriptor` structs.

### Recommended path

1. Build Model A as `tools/commrat-launch/editor.html` in CommRaT — no new dependencies, useful immediately for generating `app.json` from build output.
2. Once the metadata layers are stable, extract Model B into a `commrat-launch` repo that depends on CommRaT and can be installed via `.deb` or a distro package.

### Goal

A self-describing system where:

- **`commrat-launch editor ./build/default/examples`** opens a browser tab, scans the build dir for `*.module.json`, and lets the user wire an app visually and save `app.json`.
- The generated `app.json` is then run with **`commrat start app.json`** — same config, no duplication.

### Frontend stack

**Cytoscape.js** (bundled inline, no CDN required) handles the graph canvas: node layout, port-level edge routing, drag-to-connect, zoom/pan — without requiring a framework or build step.

### Module node visual structure

Each module is rendered as a Cytoscape compound node with three zones:

```
┌──────────────────────────────────┐
│ input ports (top)                │
│  ○─ IMUData  [10:1]              │
│  ○─ GPSData  [20:1]  (synced)    │
├──────────────────────────────────┤
│ FusionModule  "fusion"           │  ← module_class + instance name
│  system_id   [ 30 ]              │
│  instance_id [  1 ]              │
│  period_ms   [ -- ]  (derived)   │
│  ─── params ───────────────────  │
│  alpha       [ 0.8 ]             │
│  max_age_ms  [ 200 ]             │
├──────────────────────────────────┤
│ output ports (bottom)            │
│  FusedPose  ─○                   │
└──────────────────────────────────┘
```

Fields marked `(derived)` are read from the descriptor and shown greyed-out. Param fields and their defaults come from `params_defaults` in the descriptor — the editor renders typed inputs (number spinners, text fields, checkboxes) based on the JSON value types in `params_defaults`.

### Routing edge validation

When the user drags from an output port to an input port, the editor checks:

```
source descriptor.outputs[i].type == target descriptor.inputs[j].type
```

If they match, the edge is drawn and the input port address fields are auto-filled from the source output's assigned address. If they do not match, the connection is rejected with a tooltip showing both type names.

Synced inputs (from `synced_inputs[]` in the descriptor) are rendered with a distinct port colour and label.

### Editor → `app.json` export

Saves the canvas state as `AppDescription` JSON — identical format to a hand-written `app.json`, fully interoperable with `commrat start` and `ProcessLauncher`.

### Live overlay (Model B only, commrat-launch repo)

When `commrat-launch` is running alongside a live app, the topology canvas can overlay:

- Green/amber borders on modules based on recent publish activity
- Message rate badges on output ports

This requires the WebSocket stream from RaTGUI's `BridgeModule` and belongs in the separate `commrat-launch` repo, not the zero-dependency file tool.
